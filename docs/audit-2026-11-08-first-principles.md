# 第一性原理产品审计（2026-11-08）

审计对象：`@kenz1117/dsh-ui-usage-billing` @ `4a63ee8`（issue #119 修复后，v1.8.3-alpha.4）。
方法：先从「用户到底要什么」推导不可协商的不变量，再拿现状去对；**不按功能清单打分**。
证据：每条结论都有 `file:line` 或实测数字；标「实测」的为本机跑出来的，标「推导」的为按代码语义外推。

---

## 一、第一性原理：这个产品到底是什么

用户来这个插件，不是为了「看 token 数」——那是宿主自己的 footer 就有的。用户真正在问三件事：

1. **我为 AI 付了多少钱？**（一个能拿去对账的数字）
2. **这钱花得对不对 / 为什么这么贵？**（能下钻、能解释）
3. **明天怎么少花点？**（阈值、峰谷、预算）

所以这个产品**不是「token 计数器」，是本机推理支出的账本 + 解释器**。它和宿主自带的计数器有本质区别：宿主的计数器是**瞬时读数**，本插件是**账本**——有历史、有归属、有价格、有对账。

一旦把它定义为「账本」，就有 7 条不可协商的不变量。**这不是功能愿望，是账本成立的前提**：

| # | 不变量 | 含义 | 违反时的后果 |
|---|---|---|---|
| **I1 真相性** | 每个数字都要带认知状态：实测 / 预估 / 未知 | 未知不是 0，预估不是实测 | 用户按假数字做决策 |
| **I2 完整性** | 有用量就不能静默丢 | 读不到要计数、要归因 | 账单偏低且无法自查 |
| **I3 唯一性** | 同一笔调用只算一次 | fork 血缘、子智能体归并、账本+日志双源 | 重复计费 |
| **I4 归因正确** | 谁花的、什么模型、哪一天、什么价 | 时间边界与价格时间点必须唯一 | 「今日」算错天、价目被改写 |
| **I5 可核验** | 能和厂商账单对上一笔 | 逐笔可查、口径单一 | 「可对账」沦为口号 |
| **I6 新鲜度可见** | 数据何时算的、多旧、降级过没有，要能被看见 | 延迟与降级必须有标记 | 用户把旧值当新值 |
| **I7 可持续** | 用户规模上来后不崩、不拖垮宿主 | 折叠成本、磁盘、内存、事件循环 | 重度用户面板永久失灵 |

外加一条目前**成立**的不变量：**I8 克制**——本机、只读、默认不注入系统提示、外部资源失败能降级。这一条不用改。

## 二、八条不变量的现状判定

| 不变量 | 判定 | 一句话结论 |
|---|---|---|
| I1 真相性 | **✗ 破口** | wire format 只能带 `number`，「未知 / 预估 / 部分覆盖」三种状态无处表达，于是全部塌缩成 0 或无标记的实数 |
| I2 完整性 | **△** | 单会话拒读有计数与横幅，但侧栏无感；会话列表整体失败刚修好（#119）；未知路由与未收录模型被静默排除且默认隐藏 |
| I3 唯一性 | **✓ 强** | 折叠逐事件单遍、`message.source` 权威归属、fork 种子边界、子智能体只写行级 `subCost`——均有实打实的用例（见 §四） |
| I4 归因正确 | **△** | 「按事件发生时刻计价」有强测试；但**同时存在三个时钟**（§三 S5），「今日」会算错天 |
| I5 可核验 | **△** | 对账实际只覆盖 DeepSeek 官方 CNY 一条通道；导出混两套价格口径；README 承诺的「项目 / 工作区」这一级**服务端算了、界面不渲染** |
| I6 新鲜度可见 | **✗ 破口** | 5 个延迟机制只有 1 个标志位 `staleSnapshot`，且在「空账本冷闸」这种最该提示的场景语义是错的 |
| I7 可持续 | **△** | 10k 会话时：账本每 60 s 全量重写 350–680 MiB、内存 76 MiB、合并尾段阻塞事件循环 108–186 ms、面板**永远**显示「数据来自上次计算」 |
| I8 克制 | **✓** | 本机只读、外部资源有熔断与降级、无提示注入 |

**最刺眼的一条**：本仓 9 条 lint 纪律守卫（`scripts/lint.mjs`）全部是类型 / 日志 / 空 catch / CSS parity / 令牌 / 字体 / 面板压缩 / sticky / portal——**没有一条涉及折叠、账本、计价或时区**。数据正确性目前只靠单元测试兜，没有结构性守卫。

## 三、六个结构性根因（不是 30 个 bug，是 6 个设计缺口）

### S1 —— 数字没有认知状态（这是 I1 破口的根源）

系统的真实状态有三种：**实测**（服务端实算）、**预估**（目录价折算）、**未知**（算不出）。但传输层只能带一个 `number`。于是：

- 未知 → 0（#119 的整条链路、每轮图里 ¥0.000 的柱、KPI 分母为 0 时的 0.0%）
- 预估 → 与实测同形（`UsageBilling.tsx:1786` 的 `displayTotal` 回退、模型行的 `estimated`）
- 部分覆盖 → 渲染成整体（未收录模型、未知路由、订阅豁免）

**同一处代码同时是「诚实的实现」和「骗人的实现」**：`domain/kpi.ts:66` 的 `providerCostOf` 明确把订阅行归零（issue #37 的教训），而 `UsageBilling.tsx:1786` 的 `displayTotal` 在 `total.cost === 0` 时回退到含订阅行的 `estimatedTotal`——**同一页面上，厂商组头显示 ¥0、hero 累计显示 ¥38**。两个口径都"有代码、有注释、都有道理"，合起来是自相矛盾。

> 这解释了为什么 §四 的 ~20 条表象问题反复出现：它们不是 20 个独立的粗心，而是**一个数据模型缺口的 20 个投影**。

### S2 —— 一条流水线，五个延迟，一个标志位

`20s 冷闸`（`index.ts:128`）→ `5s TTL`（`aggregate.ts:703`）→ `1.5s 响应预算`（`index.ts:178`）→ `5min 快照节流`（`index.ts:173`）→ `30s / 5min 客户端轮询`。

全部只用 `staleSnapshot: true` 一个标志表达，而且**用错了地方**：

- 冷闸 + **空账本**（新装用户的第一屏）→ 标「用量正在重算，以下数据来自上一次计算」——**根本不存在上一次计算**（`aggregate.ts:2710`）。
- 磁盘快照可能是 5 分钟前，也可能是 3 天前 —— `updatedAt` 从不下发给用户（`aggregate.ts` 文档里没有快照年龄字段）。
- 预算条、余额告警、桌面通知在取数失败后**仍按旧值计算并照发**（`UsageBilling.tsx:4300-4308` 只在 `result.ok` 时更新 stats，但告警逻辑不检查错误态）。

### S3 —— 「账本」是派生品，却同时是耐久机制和规模瓶颈

宿主会话日志是**真相**，插件的 `.dsh-usage-ledger.json` 是**派生**。但插件给用户的承诺是「持久账本」——于是派生品承担了耐久责任，而它的实现是「每 60 s 全量重写整个文件」：

- 每行 2,574 B 实测；10k 会话 × 40 轮 → 账本 **68.5 MiB**，加上 `.bak` **137 MiB**
- 每 60 s：`readFile` 全读 + `JSON.parse`（130 ms）+ 写 `.bak` + 行级合并 + `JSON.stringify`（101 ms）+ 写主文件 → **350–680 MiB 磁盘 I/O + ~0.5 s 同步 CPU**
- **永不剪枝**（`aggregate.ts:2447` 注释：missing rows are history）→ 用户删掉的会话永远留在账单里，且**没有任何标记**（`staleLedgerSessions` 只统计旧算法行）
- `fingerprint` 逐行冗余 300 B × N 行（全局配置串，对所有行完全相同）
- 反序列化的 `WeakMap` 记忆把每行 3,324 B 永久钉在堆上 → **常驻内存 ≈ 账本文件 × 1.1**

### S4 —— 价格目录是真正的手写数据库，却没有任何漂移检测

`src/builtin-catalog.ts`：**248 条、2,350 行、100% 手写**。每条要人工核对 input / cacheHit / output / offPeak / peakHours / promo 窗口；厂商调价要改代码并可能 bump `FOLD_VERSION` 触发全量历史重折；促销窗口（Hy4 的 5 折至 2026-12-31）**到期要人工记得改回去**。

CI 的 5 步里没有任何一步拿内置价目表和 models.dev / 官方价目比对（`check-catalog.mjs` 校验的是 **DSH 市场目录**，不是价格目录）。

同时，客户端每 30 s 拉一次 **511 KiB** 的定价文档（catalog 43 KiB + aliases 6 KiB + models.dev extraModels 462 KiB），而费率表只显示探活匹配到的少数模型 → **60 MB/小时 loopback，17 KB/s 持续 parse**，换来的是绝大多数条目用户一辈子看不到。

### S5 —— 三个时钟同时决定「今天」和「什么时候便宜」

| 时钟 | 用途 | 位置 | 用户知道吗 |
|---|---|---|---|
| 宿主进程本地时区 | 账本的「天」（`byDay` 的键） | `aggregate.ts:392-397` | 仪表盘副标题有显示；**侧栏卡没有** |
| **北京时间 UTC+8 硬编码** | 峰谷分档判定 | `pricing.ts:318-323,344-353,398-400` | **界面零处说明**（`locales.ts` 全文无「北京」二字） |
| 浏览器本地时区 | 客户端算「今天」 | `pricing.ts:1213-1219` | 不知道 |

更糟的是**账本行不存时区**（`aggregate.ts:983-1011`）：用户换时区后，只要会话被重折一次，同一天的费用会被劈成两天；「今日 / 本周 / 本月」三个 KPI 全部受影响。而现有测试 `tests/aggregate.spec.ts:739` 的断言是 `/^2026-08-1[5-6]$/`——**测试自己声明时区随便**。

### S6 —— 产品按「分区」组织，用户按「问题」提问

8 个分区（概览 / 队列 / 账单 / 用量 / 趋势 / 智能体 / 费率 / 设置）与用户的 5 个问题并不对齐，具体割裂：

- 「今天花了多少」：侧栏卡默认 **今日**，仪表盘 hero 默认 **累计**（`usage-billing-settings.ts:131` vs `:190`）——同一屏两个数，两个周期，无交叉说明。
- 「账单对不对」：漂移告警在**概览页**，被对账的余额在**账单页**，导出按钮也在账单页——查余额时收不到告警。
- 「为什么这么贵」：README 承诺下钻到「项目 / 工作区」；服务端算了 `byWorkspace`、API 透传了、类型声明了——**客户端零渲染点**。
- 「哪一轮最贵」：逐轮图取的是**倒序数组的末 40 条**（`round-chart.tsx:67` 的 `slice(-40)`），即「最新 200 轮里最旧的 40 轮」，且图注自称 "most recent N, newest last" 与实现相反。

## 五、已经站得住的部分（不要在返工时误伤）

这些有实打实的用例支撑，审计时逐条 grep 确认过存在：

- 折叠与权威归属：`aggregate.spec.ts:476`（每条调用按自己的 `message.source` 归属）、`:504`（重折不回归）
- fork 血缘 5 条用例：`:591 / :607 / :630 / :647 / :675`
- 增量 == 全量：`:1213`；seq 跳号退回全量：`:1238`
- 账本快路径零读取：`:1265`；节流 + flush：`:1494`
- 拒读负缓存（内存 / 落盘 / stamp 变化后重试）：`:1417`、`aggregate-replay-gate.spec.ts:125`
- FOLD_VERSION 迁移幂等：`:1719 / :1731 / :1746`
- 惰性重价与配置指纹触发重折：`:2011 / :2053 / :2088 / :2136 / :2236 / :2281 / :2417`
- 按事件时刻计价：`pricing.spec.ts:677`（历史保留当时价格）、`:958`（促销起点前不追溯）
- 未知路由零计价：`:814 / :830`；账本文件原子性与多实例合并：`ledger.spec.ts` 全组

**换句话说：账本的"算法"是可靠的，可靠性破口全在"怎么把结果讲给用户"和"规模上来之后"这两头。**

## 六、建议批次（按仓库纪律排：只改呈现不改口径 → 扩口径 → 补规模）

### 批次 1 · 可信度（只改呈现，不动任何计价口径）

1. **给数字加认知状态**：wire format 增加一个可选的 `estimated` / `unknown` 标记位；客户端统一「未知 → —，不是 0」。这一条落地后，S1 投影出来的 ~20 条表象问题一次性消掉大半。
2. **累计总额不静默切预估**（P0-1）+ 预估值加 `≈`（与模型行现有语义对齐）。
3. **未知 / 未收录常驻提示**（P0-2）：不靠可关闭横幅，含名单 + 修复入口。
4. **修正逐轮窗口**（P0-4）与**热力图区间口径**（合计 / 活跃天数按当前 range 重算）。
5. **快照年龄与降级原因可见**（S2）：`updatedAt` 已下发给客户端，直接展示「数据算于 X 分钟前」；把 `staleSnapshot` 拆成「正在重算 / 上次计算 / 读取失败」三态。

### 批次 2 · 口径与时钟

6. **统一时钟**（S5）：账本行记 `tz`；峰谷改用宿主时区或显式声明「峰谷按北京时间」；补固定 TZ 测试，替掉现在那条 `/^2026-08-1[5-6]$/` 的宽松断言。

## 七、一句话结论

**账本的算法是可靠的，讲账的语言是不可靠的。**

折叠、归属、计价时间点、账本原子性都有实打实的用例守着；破口集中在两处：**数字没有认知状态**（未知 / 预估 / 部分覆盖全塌缩成 0 与无标记的实数，产出约 20 条表象问题），以及**规模上来后的结构**（单一派生文件既是耐久机制又是瓶颈，10k 会话时面板会永久显示「数据来自上次计算」）。

下一轮最划算的动作不是加功能，而是**给数字加状态**：一个可选标记位 + 客户端「未知 ≠ 0」的纪律，能一次性把用户信任成本最高的一批问题变成非问题。
